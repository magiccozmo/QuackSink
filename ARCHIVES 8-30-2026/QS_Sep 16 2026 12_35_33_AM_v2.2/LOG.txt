The patch system. A patch is a mutation applied to the game state. Increase X, decrease Y, invert Z, disable interaction, swap two card effects. These are functions that take the world state and return a modified world state. Python eats this for breakfast.
The simulation. Testing the game without a human is where Python shines — and this is actually the killer feature. 🔮 DeepSeek - 🦆 Kelp here. Quick answer before you and Gem go install: Ollama doesn't present a browser tab, and QS will need new infrastructure to talk to it.
But it's good new infrastructure, and much simpler than the DRS stack.
Why there's no browser tab to attach to:
The QS relay works by driving browser tabs via the Chromium Remote Debugging Port. It finds a tab, reads the DOM, types into an input box, captures the output. That works because ChatGPT, Gemini, etc. are web pages.
Ollama is a local HTTP server. It listens on http://localhost:11434 by default -
22
-
27
. It doesn't render a UI. It just answers API calls. There's no DOM for Luma to inspect, no input selector for the DRS to type into. The browser-tab model simply doesn't apply.
What QS actually needs to talk to Ollama:
Ollama exposes an OpenAI-compatible API at http://localhost:11434/v1/ -
1
. That means your Python code (or the DRS, or a new module) can talk to it exactly like it talks to OpenAI's API — same format, same endpoints, same request shape.
So the new infrastructure is roughly:
An HTTP client in Python. requests or httpx. Send a POST to http://localhost:11434/v1/chat/completions with the message history, get a response back.
A new "node type" in the DRS config. Instead of a url and input_selector, an Ollama node has a base_url and a model name. The relay loop branches: if it's a browser node, drive the tab; if it's an Ollama node, make the HTTP call.
The FIFO stack and token logic stay the same. Ollama doesn't need 🟩 and 🔚 for synchronization — you control when you call it. But you'd still want the DRS to format the prompt with the same message stack, and you'd still want the response placed onto the other nodes' stacks.
The honest scope:
It's a new transport layer, not a new relay. The DRS already has the concept of "a node that produces text and receives text." Ollama is a node that produces text over HTTP instead of over a browser tab. The relay logic, the FIFO, the fan-out — all of that stays. You're swapping the pipe, not the plumbing.
One concrete thing to note: Ollama's API has no authentication by default and binds to 127.0.0.1 -
24
. That's actually good for QS — it means your local QS process can talk to it freely without tokens or keys. You'd set api_key='ollama' in the OpenAI client but it's ignored -
1
. The security model is "it's local, nobody else can reach it unless you explicitly expose it."
So: not a browser tab. A local API. QS gets a new node type, a new HTTP client, and the same relay logic on top. It's a Saturday afternoon project, not a rewrite.
