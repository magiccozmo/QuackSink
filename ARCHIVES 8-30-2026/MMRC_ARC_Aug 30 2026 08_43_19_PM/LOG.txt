Investigation: Attaching to an Existing Browser Instance

The Core Question: What happens when a Chromium browser (Edge, Chrome, Opera) is already running normally—i.e., launched without --remote-debugging-port—and MMRC attempts to attach via CDP?

The Short Answer: It will fail to connect. Playwright's connect_over_cdp requires an active debugging endpoint. If the browser wasn't launched with the flag, that endpoint doesn't exist.

The Nuance:

No Port, No Connection: A normally-launched browser does not listen on a debugging port. connect_over_cdp("http://127.0.0.1:9222") will time out or refuse the connection because nothing is listening.

Multiple Instances: On Windows, a user may have multiple browser processes running—some launched normally, others with debugging enabled. The CDP endpoint only exists for the instance(s) launched with the flag.

Re-attachment: If the user previously launched a browser with --remote-debugging-port, closed it, and then opened a new instance normally, the old endpoint is gone. The new instance won't have the flag.

Recommendations for Windows Launch Behavior:

Probe First: Before attempting to launch anything, MMRC should try to connect to the default CDP endpoint (or any configured endpoint). If a connection succeeds, use it. This is the least intrusive path.

Fallback Launch: If no CDP endpoint is found, present the user with a list of detected Chromium browsers (from the system PATH or common install locations). Ask them to select one, then launch it with:

--remote-debugging-port=9222

--user-data-dir=C:\path\to\a\new\profile (to avoid interfering with their normal session)

The browser's executable path.

Verification: After launching, wait for the endpoint to become available (polling with a short timeout). Then proceed to MMRC's normal discovery.

The "Already Running" Edge Case:

If the user already has a browser running, but it was launched without the flag, MMRC has two options:

Warn the user: Inform them that a browser is detected but not debuggable, and ask if they want to close it and re-launch with the flag.

Launch a new instance: Use a separate user data directory to launch a fresh instance with the flag. This leaves their existing session untouched.

Option 2 is safer and less disruptive. The user can keep their normal browsing session intact while MMRC runs in a separate, debuggable instance.

Key Engineering Findings:

The CDP endpoint is not persistent across browser restarts unless the launch command includes the flag.

Windows does not provide a built-in way to "attach" to a running process and enable CDP without restarting it.

The safest approach is to:

Probe for existing debuggable instances.

If found, attach.

If not, offer to launch a new instance with the flag (using a separate profile).

This keeps the user experience smooth and avoids disrupting their existing work.

Engineering Findings: Navigating the "Browser Running Without CDP" Edge Case

Building on Kelp's analysis, here are the technical mechanics on Windows and how MMRC can handle existing non-debuggable processes gracefully:

1. Why Attaching to a Standard Running Instance Fails

On Windows, Chromium browsers (Chrome, Edge, Opera, Brave) run a single primary browser process.

If a user already has Edge or Chrome open normally (launched via desktop icon/start menu without --remote-debugging-port), running msedge.exe --remote-debugging-port=9222 from a script will not start a debuggable instance by default.

Instead, Windows simply passes the open command to the existing running browser process, which ignores the new command-line flags and opens a standard tab in the current window.

Result: Port 9222 remains closed, and connect_over_cdp throws a connection refused error.  
PY

2. The Solution: Isolated Dev Profile (--user-data-dir)

To guarantee that launching a browser with --remote-debugging-port=9222 actually spawns a new debuggable process—even while the user has their personal browser open—MMRC must pass a dedicated user profile directory.

Launch Command Spec (Windows):

DOS
msedge.exe --remote-debugging-port=9222 --user-data-dir="%LOCALAPPDATA%\QuackSink\EdgeProfile"


Why this works:

The --user-data-dir flag forces Chromium to launch a clean, independent process tree that honors --remote-debugging-port=9222.  
PY

The user's regular personal browser windows remain completely untouched and safe.

Logins inside QuackSink's profile (ChatGPT, Claude, Gemini, DeepSeek) persist across sessions inside that dedicated folder.  
PY

3. Probing Mechanics (Probing vs. Guessing)

To distinguish between "Browser exists" vs. "CDP is actually attachable":

HTTP GET Probe: Before trying to connect Playwright, issue a fast socket or urllib/aiohttp GET request to [http://127.0.0.1:9222/json/version](http://127.0.0.1:9222/json/version).

If HTTP 200 OK: CDP is active and ready! Immediately hand off to connect_over_cdp.  
PY
+ 1

If Connection Refused / Timeout: Port 9222 is closed (no CDP browser active). Trigger the Browser Launch Helper.  
PY

Sequential Launch Verification Loop:

User selects browser (Edge / Chrome / Opera).

MMRC executes the binary with --remote-debugging-port=9222 --user-data-dir=...

MMRC polls [http://127.0.0.1:9222/json/version](http://127.0.0.1:9222/json/version) up to 5 seconds.
