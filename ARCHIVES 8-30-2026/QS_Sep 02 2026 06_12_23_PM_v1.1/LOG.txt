In 2.0 I want the architecture to read almost like the specification itself:

ADDRESS
   │
   │  proven browser/mailbox mechanics
   ▼
MAILBOX ADAPTER
   │
   ▼
🦆 DUCKMAIL ENGINE
   ├── Delivery List
   ├── current route position
   ├── Duck-owned pockets
   ├── HUMAN pocket
   ├── Flight Log
   └── delivery/response state

So Node becomes an address/mailbox descriptor, not the owner of mail.

The Duck becomes the owner of all undelivered cargo:

duck.pockets[address] = FIFO deque

And the one really sacred operation is:

pickup → log actual message → copy to destination pockets

while delivery is:

attempt
   ↓
success?
  ├─ YES → remove exactly what was successfully delivered
  └─ NO  → remove NOTHING

That last branch is the reliability heart of Duckmail.

The other big architectural correction is that discovery, route membership, and delivery are three different things. 1.1's HANDSHAKED state currently makes a node “active,” but 2.0 needs the browser tab to be merely an address until Cozmo puts it on the Delivery List and the Duck completes the invitation handshake. 
GitHub

I also want the Flight Log separated from the ordinary diagnostic logger. The existing file logger is already real-time and append-based, which is excellent and stays. 
GitHub
 But the Duck's mail history needs explicit records of the actual message payloads picked up, not just “GPT replied.” That becomes a first-class QS 2.0 data structure and gets written to the live log as it happens.

For the UI, I'm keeping the proven bones rather than redesigning everything at once. But the center becomes Duckmail:

DISCOVERED ADDRESSES

DELIVERY LIST
1. ...
2. ...
3. ...

DUCK STATUS
🦆 Visiting: ...
📬 Pocket: ...

MESSAGE TO DUCK
[.....................]
[ SEND ]

HUMAN MAILBOX
[ TOP ] [ BOTTOM ]
[.....................]

☑ Show status messages

[COPY LOG]
[NOTES / SAVE NOTE]

And SEND is disabled whenever the Duck is in flight. At route completion it becomes available again, and pressing it returns the Human mailbox viewport to TOP before the next trip.

One thing I want the three of you to attack before I start coding:

Find edge cases in the Duckmail state machine.

1. A node becomes unavailable after Duck has already begun delivering.
2. A node answers, but its response is not a valid message.
3. A node produces multiple new frames.
4. A pocket contains several messages and delivery fails halfway through.
5. New mail arrives for an address while Duck is visiting another address.
6. A route member is removed while pockets still contain undelivered mail.
7. SEND is pressed at an awkward moment.
