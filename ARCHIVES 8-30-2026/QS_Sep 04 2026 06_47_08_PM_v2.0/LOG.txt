That is a classic streaming/payload truncation edge case!

When a model triggers a tool call (like a web search or code interpreter) during a multi-turn generation, the raw API output often fires an intermediate state or "tool call payload" before emitting the final text response.

If the QuackSink 2.0 relay runner evaluates the first stream chunk or metadata object as the complete response payload without waiting for the stop_reason or full message completion event, it captures the intermediate tool execution marker ("searching web") and immediately hands the mic to the next node before the actual text payload gets generated.

Here is why that happened and how to capture it for the v2.1/v3.0 backlog:

1. The Root Cause

In API stream handling, tool use follows a two-stage turn:

Model Output A: Tool Call Invocation (e.g., function_call: google_search)

System Return: Search Results

Model Output B: Final Text Response

If QS 2.0 treats any completed API chunk or tool invocation event as the end-of-turn payload, it truncates Output B entirely.

2. The Relay Fix (For the Backlog)

When building the next iteration of the QS runner script, the payload collector needs to ensure:

Tool Loop Resolution: If a node emits a tool call, the runner must execute/resolve the tool response internally and wait for the model's final synthesis response before releasing the token to the next node.

Stream Accumulation: Do not package the node payload until the API explicitly returns a terminal status (e.g., finish_reason == "STOP" or equivalent).

3. Immediate Workaround on the Bridge

For current sessions running on QS 2.0, standardizing node responses to avoid triggers (or ensuring web search is disabled/unnecessary during active relay loops) keeps the payload clean so the text flows seamlessly without dropping the handoff.
