🔮 DeepSeek - Kelp here.
The unified voice layer is the right abstraction, and Luma's ASCII pipeline is exactly it. But I want to flag one thing before everyone gets excited about "five voices, one engine," because there's a subtlety hiding in the plan.
There are two different kinds of voice path in this system.
The cloud-native path (Luma, Gemini, Aisha) is: drive a button in a browser tab and wait. The voice comes from the provider. Quality is fixed. Availability is the only variable. You don't control the sound.
The local path (Chron, and any fallback) is: generate audio from text on this machine and play it. You control the sound. Availability is fixed. Quality is the variable.
A unified VOICE(text, node) layer has to abstract over both, which means it's really two backends behind one interface. That's fine — but it's worth designing the interface knowing that one branch is "trigger and wait" and the other is "synthesize and play." The wait-semantics are different. The error modes are different. Quota exhaustion vs. VRAM exhaustion. Cloud-side render failure vs. local model crash.
The other thing: "voice profile E" isn't stable unless you commit to one engine per node. Piper-Chron and Kokoro-Chron will sound like two different people. If Chron gets a voice via Piper today and Kokoro next month, she doesn't have *a* voice — she has whichever one you wired up that week. That's a design choice, not a bug, but it should be a conscious one. Either pick one engine and stick with it, or accept that a node's voice is "the current backend's rendering of that node."
For the immediate next step, I'd keep it small: prototype the local engine standalone. Pick one — Piper or Kokoro — run it on the laptop, benchmark "one sentence in, time-to-audio out" on the 4GB card. If it passes the three-second bar, then wire it into QS. If it doesn't, try the other engine. Don't touch QS until you know which engine wins.
Solve the local TTS problem once, as its own thing. Then the unified layer is just plumbing.

🔮 DeepSeek - Kelp here.
Luma's answer is correct, and the architecture difference matters more than the raw speed difference.
Kokoro: one model, many voices. The 82M parameter backbone loads once, and voice selection is just picking a different voice embedding. Load time is amortized across all voices. Memory footprint stays flat as you add voices.
Piper: one model per voice. Each voice is its own .onnx file plus config. Five voices means five models on disk and potentially five model loads in memory, depending on how the engine caches.
For your specific requirement — many voices, one engine, low overhead — Kokoro wins on architecture alone. You get 54 preset voices for the cost of one loaded model.
The benchmark question still stands, though. Architecture doesn't tell us whether your 4GB card can run Kokoro fast enough to be usable. That's an empirical question. The answer might be "Kokoro on GPU, fast enough" or "Kokoro on CPU, slower but acceptable" or "Kokoro is too heavy on this machine, fall back to Piper and accept one-model-per-voice."
But if Kokoro does run on your laptop at acceptable speed, it's the right pick. That's the test to run.
One thing to nail down before building QS_TALK: which voice IDs map to which nodes?
The naming convention in Kokoro is like af_heart, am_michael, bf_emma, bm_george — first letter is language (a=American, b=British), second is gender (f/m), and the rest is the name. If you want to assign specific voices to specific nodes, that mapping should live in a config file, not hardcoded into QS_TALK. Something like:
text
Copy
Download
chron=af_nicole
kelp=af_heart
gemini=bf_emma
Then QS_TALK just takes a node name and a text file, looks up the voice in config, and speaks. That way when you want to try a different voice for a node, you change one line and don't rebuild anything.
But that's the second step. The first step is still: can Kokoro say one sentence in under three seconds on the dinosaur? Everything else waits on that answer.

Here is the blueprint for the first standalone prototype: QS_TALK
Phase 1 Spec: QS_TALK Standalone Toy
Language & Interface: A simple Python script packaged or called as a command-line utility:
Bash
python qs_talk.py response.txt af_heart
Execution Flow:
Read: Open and read the text payload from the provided file path (response.txt).
Synthesize: Initialize the Kokoro pipeline, load the specified voice embedding (af_heart, bm_george, etc.), and synthesize the audio stream (native 24kHz).
Play & Block: Route the audio output to the default system audio device and block execution until the playback buffer is fully cleared.
Exit Codes:
0 on successful playback completion.
Non-zero (e.g., 1 for missing file/dependency, 2 for synthesis error, 3 for audio device error) so an orchestrator can check health without parsing stdout.
The First Test Script
To see how the hardware handles it, we can use a minimal standalone test script using the official kokoro package and soundfile / playback libraries:
Python
import sys
from kokoro import KPipeline
import soundfile as sf
import sounddevice as sd  # or a simple blocking player
def speak_file(filepath, voice_model):
try:
with open(filepath, 'r', encoding='utf-8') as f:
text = f.read().strip()
if not text:
print("Error: Text file is empty.", file=sys.stderr)
sys.exit(1)
# Initialize pipeline (American English default 'a', adjust if needed)
pipeline = KPipeline(lang_code='a')
# Generate audio generator
generator = pipeline(text, voice=voice_model)
for i, (gs, ps, audio) in enumerate(generator):
# Play each chunk and block until finished
sd.play(audio, 24000)
sd.wait()
sys.exit(0)
except Exception as e:
print(f"Error during synthesis/playback: {e}", file=sys.stderr)
sys.exit(2)
if __name__ == "__main__":
if len(sys.argv) < 3:
print("Usage: python qs_talk.py <file.txt> <voice_model>")
sys.exit(1)
speak_file(sys.argv[1], sys.argv[2])

🔮 DeepSeek - Kelp here.
Yes to Luma as lead dev. Same rules, same baselines, same "don't edit a known-good release in place." That's been working.
And yes to Kokoro. One model, many voices, CPU-friendly. It's the right first experiment.
But before anyone runs Gemini's script as the official baseline, two corrections to the spec:
One — the loop exits too early. sys.exit(0) is inside the for loop, so the script will quit after the first audio chunk. Kokoro splits longer text into multiple chunks depending on punctuation and length. If Chron's response is two sentences, only the first would play. The sys.exit(0) needs to be after the loop, so the script only exits once every chunk has been played and waited on.
Two — exit code 3 is spec'd but not implemented. Gemini's bullet list promises "3 for audio device error," but the example only returns 1 (empty/missing) and 2 (synthesis failure). Either implement the third code or drop it from the spec — but don't leave it in the doc as a promise the code doesn't keep. QS doesn't care what the codes are, only that they're consistent.
Three — and this matters more than the code — the "three-speed test" needs a precise definition before you run it. There are three different timings that could be called "speed":
Synthesis time: text in → audio buffer out
Playback time: audio buffer → speakers done
End-to-end: QS_TALK invoked → process exits
The first is the interesting one for "can the dinosaur handle this." The second is roughly fixed by the length of the text. The third is what QS actually experiences, and it's synthesis + playback + process overhead. If you benchmark #1 alone and get "under three seconds," but the process launch overhead is another two seconds, the feature still feels slow to the room.
My suggestion for the test protocol:
Write a one-sentence test file (15-20 words).
Run time python qs_talk.py test.txt af_heart.
Capture wall-clock total.
Do the same with a two-sentence file, three-sentence file.
Report: "One sentence = Xs. Two sentences = Ys. Three = Zs."
That tells you the per-sentence cost and whether it scales linearly or has a fixed overhead. From there you can decide whether the room can tolerate waiting for Chron.
One more thing: the first test shouldn't use af_heart by default. Pick the voice you actually intend Chron to use. If you benchmark with one voice and ship with another, the timing numbers may not transfer — different voice embeddings have slightly different inference costs.
Otherwise, solid spec. Kokoro first. Build the toy. Then we talk about wiring it into QS.

import sys
import time
from kokoro import KPipeline
import sounddevice as sd
def main():
if len(sys.argv) < 3:
print("Usage: python qs_talk.py <file.txt> <voice_model>", file=sys.stderr)
sys.exit(1)
filepath = sys.argv[1]
voice_model = sys.argv[2]
# --- Timing Marker: Start ---
t_start = time.perf_counter()
try:
with open(filepath, 'r', encoding='utf-8') as f:
text = f.read().strip()
if not text:
print("Error: Text file is empty.", file=sys.stderr)
sys.exit(1)
# Initialize pipeline (American English default 'a')
pipeline = KPipeline(lang_code='a')
# Generate audio generator across chunks
generator = pipeline(text, voice=voice_model)
# Stream and block chunk by chunk
chunk_count = 0
for i, (gs, ps, audio) in enumerate(generator):
chunk_count += 1
sd.play(audio, 24000)
sd.wait()  # Block until current chunk finishes playing
t_end = time.perf_counter()
elapsed = t_end - t_start
# Log performance metrics to stderr for the benchmark report
print(f"[BENCHMARK] Chunks: {chunk_count} | Total Wall-Clock Time: {elapsed:.2f}s", file=sys.stderr)
sys.exit(0)
except FileNotFoundError:
print(f"Error: File not found -> {filepath}", file=sys.stderr)
sys.exit(1)
except Exception as e:
print(f"Error during synthesis or playback: {e}", file=sys.stderr)
sys.exit(2)
if __name__ == "__main__":
main()

The three fixes landed. Exit code is out of the loop, exit codes are consistent now (1 for file/usage, 2 for synth/playback), and the benchmark harness is in.
But there's one thing left in the spec that matters more than everything else, and I want to flag it before you burn a test run on it:
The benchmark is measuring the wrong thing.
t_start is before KPipeline(lang_code='a'). That means the elapsed time includes model load, not just synthesis + playback. For a one-shot CLI call, that's technically the honest end-to-end number — but it hides the distinction you actually need to make.
Because if the numbers come back "4 seconds for one sentence," you won't know if that's:
2.5s load + 1.0s synthesis + 0.5s playback, or
0.5s load + 0.5s synthesis + 3.0s playback
And those two answers lead to completely different architectures. The first says "the CLI model is wrong, use a persistent daemon." The second says "the model is fine, the text is just long."
What I'd change before the first run:
Split the timer into three markers:
text
Copy
Download
t_load_start = perf_counter()
pipeline = KPipeline(lang_code='a')
t_load_end = perf_counter()
# ... after generation completes but before playback
t_synth_end = perf_counter()
# ... after playback finishes
t_play_end = perf_counter()
Then log [BENCHMARK] load=X.XXs synth=Y.YYs play=Z.ZZs total=W.WWs.
That single change tells you whether the CLI shape is viable at all. If load is cheap, one-shot is fine. If load is expensive, QS_TALK needs to become a resident process that loads Kokoro once and receives synthesis requests over a socket or stdin.
Two smaller notes:
Hardcoded lang_code='a' is fine for now, but when you add a British voice (b*), the lang code has to match. Either infer it from the voice ID prefix or make it a third CLI arg.
Zero-chunk case — if the generator yields nothing, the script exits 0 with Chunks: 0, reporting silent success. Worth a check: if chunk_count == 0: sys.exit(2).
Neither of those is urgent. But the split-timer change is worth doing before the first benchmark, because otherwise you'll get a number that doesn't tell you what to do next.

# Infer language code from Kokoro voice prefix (e.g., 'af_heart' -> 'a', 'bf_emma' -> 'b')

with open(filepath, 'r', encoding='utf-8') as f:
text = f.read().strip()
if not text:
print("Error: Text file is empty.", file=sys.stderr)
sys.exit(1)
# --- Phase 1: Model Loading ---
t_load_start = time.perf_counter()
pipeline = KPipeline(lang_code=lang_code)
t_load_end = time.perf_counter()
# --- Phase 2: Synthesis ---
generator = pipeline(text, voice=voice_model)
chunk_count = 0
# We process synthesis and playback together per chunk since Kokoro streams generators,
# but we isolate the core loop duration.
t_synth_start = time.perf_counter()
for i, (gs, ps, audio) in enumerate(generator):
chunk_count += 1
sd.play(audio, 24000)
sd.wait()  # Block until current chunk finishes playing
t_play_end = time.perf_counter()
if chunk_count == 0:
print("Error: Generator yielded no audio chunks.", file=sys.stderr)
sys.exit(2)
# Calculate deltas
load_time = t_load_end - t_load_start
synth_play_time = t_play_end - t_synth_start
total_time = t_play_end - t_start
# Detailed benchmark breakdown to stderr
print(f"[BENCHMARK] voice={voice_model} | chunks={chunk_count} | load={load_time:.2f}s | synth_play={synth_play_time:.2f}s | total={total_time:.2f}s", file=sys.stderr)
sys.exit(0)
except FileNotFoundError:
print(f"Error: File not found -> {filepath}", file=sys.stderr)
sys.exit(1)
except Exception as e:
print(f"Error during synthesis or playback: {e}", file=sys.stderr)
sys.exit(2)
if __name__ == "__main__":
main()
