Yes. That's the direction. But I want to sharpen one part before we eventually code it.

The startup behavior should be:

1. QuackSink starts.

2. It looks for compatible browser sessions already exposing CDP.

If it finds one, use it. No unnecessary browser launch.

3. If none is available, QuackSink asks the human which supported browser to launch.

4. QuackSink launches that browser itself with the required CDP configuration.

5. QuackSink connects and proceeds normally.

And crucially, the user should never need to know that --remote-debugging-port=9222 exists.

One architectural decision I want us to preserve

Don't make the detection logic synonymous with "find a browser process."

What we actually care about is:

Can I establish a usable CDP connection to a compatible browser?

A browser process existing doesn't necessarily mean MMRC can attach to it.

So the discovery hierarchy should eventually be something like:

CDP availability → usable browser context → pages → nodes

rather than:

process exists → assume it's usable.

That distinction will save us headaches.

Current relay engine ← CDP connection layer ← browser discovery/launch layer
